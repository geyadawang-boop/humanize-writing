## 填写与机器读取约定

- 一行只写一条事实，不保留示范行。周期选“短期 / 中期 / 长期”之一；类型按人物、世界观、剧情、道具、情感选择。
- 章号用 `第21章` 或 `21`；支持 `第二十一章`。回收计划可写 `第20–30章`（以第30章为期限），不要写“下卷高潮”后期待脚本自动理解。发酵记录用 `第10章、第18章`；没有实际发酵写“无”。
- 状态选一项：计划中 / 未埋设 / 待埋设 / 未生效 / 未发酵 / 发酵中 / 已埋设 / 未回收 / 待回收 / 逾期 / 已回收 / 已废弃 / 留续作 / 已取消。不要把选项列表填在数据单元格里。
- 当前章号以前已埋设、未处置的行才进入逾期比例的分母。未来章或明确未埋设行不进入当前负担；计划发酵不能写入“发酵记录”冒充已发生事实。
- “处置说明”记兑现位置、已删改的前文、或续作承接和本书已兑现的承诺。旧九列表可写 `留续作：外传解释来历，本书开锁承诺已在第18章兑现`。纯“待处理”“以后再说”不构成具体处置。
- 缺文件、缺列、错行、重复ID、无法解析的章号、空表/占位表会返回检查不完整，不会把它们计为健康。内容含竖线时用 `|` 转义，避免错列。

## 回收期限和唤醒窗口分别管理

1. **已填回收计划优先**：各周期均按“预计回收章节”判断；当前章超过计划终点才报逾期。计划仍在未来时，不因短/中期默认年龄窗口强行改判逾期。调整计划要同步记录原因，不能为消除预警悄悄顺延。
2. **没有回收计划**：短期默认以埋后15章、中期默认以埋后50章作临时审计窗口，并提示补计划；长期没有统一章数期限，需按全书结构填写高潮前的兑现点。它们是从既有经验建议转成的可配置默认值，不能当成文学规律。
3. **唤醒独立检查**：从最近一次已发生的埋设/发酵章计算间隔。长期默认超过50章提醒；中期默认超过100章提醒，仅是按每卷50章估算“两卷”的占位换算。实际卷长并不固定，应按项目修改 `--mid-wake-gap`，不能宣称所有中期伏笔必须在100章唤醒。
4. **两种钟不互相抵消**：唤醒维持记忆，不等于兑现；回收计划很远，也不自动豁免发酵。脚本不推断读者已经忘记，只把超出项目窗口列为人工审查项。
5. **可用唤醒方式**：角色回忆、他人重提、物件再现、平行对照；选择能推动当下场景的一种，不为补表机械复述。

例：`python -B ledger_check.py 项目目录 --current-chapter 60 --mid-gap 40 --mid-wake-gap 70 --long-wake-gap 45`。参数只调整本次审计，项目应记录采用值，后续一致使用。

## 收支与完结处置

- 原知识的每10章收支、重大反转多次预埋等建议，仍需结合题材和实际正文人工审阅；脚本未自动证明这些条件成立。
- 逾期超过5项或占已生效未处置行的20%以上，默认报红线供集中审查；小样本比例易触发，应结合重要性判断，不为压比例批量添加未来行。
- `--final` 要求所有伏笔有终态处置。计划中、未埋设、发酵中或“计划本卷回收”都不是已完成；未来计划项也必须明确取消、落实或移交，不能藏在未来章里躲过完结审计。
- “已废弃 / 留续作 / 已取消”在完结时必须有具体处置说明。已回收应记录实际章与兑现方式；旧表仅写“已回收”仍可被读取，但机器不核验正文内容，不能据此宣布伏笔实际写好了。
- 最终仍要做反向铺垫、事实一致性和读者承诺审查，并把结论记录在项目完结检查中。
